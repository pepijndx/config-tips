Eisen & Wensen-document: een complete template voor epics, features en user stories

Door Emma van der Berg
Gepubliceerd op 2 mei 2025
Leestijd: 9 minuten

Het Eisen- & Wensen-document vormt de ruggengraat van elk software-project: het beschrijft epics, features, user stories en de Definition of Done op één centrale plaats. Hiermee ontstaat een gedeeld begrip van wat gebouwd wordt en waarom. In deze gids vind je een kant-en-klare opzet met voorbeelden die je direct kunt kopiëren naar je eigen project.

Inhoud

  • Voorblad
  • Epics
  • Features per rol
  • User stories & acceptance-criteria
  • Definition of Done

Voorblad

Het voorblad bevat informatie zoals:

  • Werkproces: Plannen van werkzaamheden en bewaken van de voortgang
  • Code: B1-K1-W1
  • Examenopdracht 1: onderdelen 1 en 2
  • Individuele opdracht.
  • Naam: Jouw naam
  • Klas: Jouw klas.

Deze informatie zorgt dat het document mooi overzichtelijk is voor de docent.

Epics

Noteer elke epic als E‑nummer met een korte beschrijving. Bijvoorbeeld:

Voorbeeld Epic

E1: Registratiesysteem – de applicatie beheert aan-/afmeldingen voor apk-keuringen en kleine reparaties.

Features per rol

Schrijf per gebruikersrol de features op als F‑nummer:

Manager (Hoofdbeheerder)

F1 Authenticatie & autorisatie
F2 Afsprakenbeheer

Automonteur (Interne gebruiker)

F3 Werkorders
F4 Statistieken & trends

Klant (Externe gebruiker)

F5 Online afspraken boeken
F6 Facturatie & betalingen

Deze indeling maakt direct duidelijk welke waarde elke rol ontvangt.

User stories & acceptance-criteria

Structureer een user story altijd als:

Als [rol],
wil ik [functionaliteit],
zodat [reden].

Voorbeeld user story US1

Manager – F1 Authenticatie & Autorisatie

Als manager wil ik kunnen inloggen met mijn inlog­gegevens zodat ik toegang krijg tot de applicatie met verhoogde rechten.

Acceptatiecriteria:

  • [AC1] E-mail en wachtwoord zijn verplichte velden
  • [AC2] Na succesvol inloggen wordt de manager doorgestuurd naar de homepagina

Prioriteit: 1 (Must) – Essentieel voor toegang tot het systeem.

Gebruik de MoSCoW-methode (Must, Should, Could, Won’t) om de prioriteit per story vast te leggen.

Definition of Done (DoD)

Alle user stories zijn pas “done” wanneer ze voldoen aan de volgende checklist:

  • Code voldoet aan de afgesproken standaarden en is gerespecteerd in een pull-request
  • Minstens één teamlid heeft de code gereviewd en alle feedback is verwerkt
  • Functionele en technische documentatie is bijgewerkt
  • Alle unit-tests slagen en nieuwe functionaliteit heeft eigen tests
  • Alle acceptance-criteria van de user story zijn behaald
  • De oplossing is performance-bewust en introduceert geen regressies

Door deze definitie op te nemen voorkom je interpretatie­verschillen over wat “af” is.
